在修复数据连接、建立版本基线和统一规则前，不建议启用无人值守的每日自动流水线。

## 四、关键发现与风险

### P0 — 真实行情链当前不可用

实际执行：

```text
atlas_py market_data.py AAPL --no-save
→ Failed to connect ... over proxy 127.0.0.1:7897
```

虚拟环境中存在 `atlas_auto_proxy.pth`，Python 每次启动都会自动注入 HTTP/HTTPS 代理。当前 7897 端口没有监听；`/tmp/verge/verge-mihomo.sock` 虽存在，但读取 Clash 配置也连接失败。因此旧报告中的“YF 真实数据可用”是历史验证结果，不代表当前运行状态。

影响：所有依赖 yfinance 的行情、估值、风险和晨报模块都可能失败，或进入各自的降级分支。

### P0 — 降级数据可能污染决策语境

`drawdown_analyzer.py`、`recovery_analyzer.py`、`risk_cluster.py` 仍保留 `REFERENCE` 路径。保留参考数据本身没有问题，但系统必须做到：

1. 真实数据失败时明确标记整次运行 degraded / failed；
2. 参考数据不得与当日真实计算结果混合展示；
3. 晨报和通知标题必须显著显示数据状态；
4. 不能基于 REFERENCE 输出可执行的仓位或交易建议。

### P1 — 没有版本回滚基线

Git 仓库尚无首次提交。Codex 可以维护代码，但当前任何修改都缺乏可靠的差异比较和回滚锚点。这是接手工程维护前最优先的治理事项之一。

### P1 — 代理入口职责不一致

- `atlas_py`：只选择虚拟环境解释器。
- `.pth`：对所有该环境中的 Python 进程全局注入代理。
- `atlas_run.py`：配置代理，并尝试修改 Clash 模式。

三者职责重叠但行为不同。尤其 `atlas_run.py` 会修改外部网络工具状态，不应作为普通脚本入口静默执行。

### P1 — 安全凭据硬编码

Clash 控制认证字符串直接存在 `_atlas_proxy.py` 和历史基础设施报告中。即使它目前只是本机控制端凭据，也应移至权限受控的环境配置，并避免继续写入报告或 Git 历史。

### P1 — 投资规则存在多处来源

现有自审计已指出 `MEMORY.md`、`risk_budget.md` 和风险角色文件中的单股/行业仓位阈值不一致。在规则没有单一权威来源前，自动化只能做信息报告，不应生成确定性再平衡指令。

### P2 — 测试入口没有遵循统一环境

`test_research_engine.py` 内部用系统 `python3` 和 shell 字符串启动子脚本，还会生成研究报告。这会绕过 `atlas_py` 的环境承诺，也不是无副作用测试。当前更准确地说，它是“端到端生成脚本”，不是稳定的自动测试套件。

### P2 — 输出与文档分散

项目有多个模块级 `reports/` 目录，同时保留旧 `daily/` 与新 `investment/reports/daily/` 体系。现阶段不建议移动文件；先增加索引和当前入口说明，避免破坏历史引用。

## 五、建议的双系统整合方案

### 职责边界

| 层 | 负责 | 明确不负责 |
|---|---|---|
| OpenClaw | 对话、长期偏好、每日任务入口、结果通知、人工确认 | 修改核心模型、静默交易、维护第二套计算逻辑 |
| Codex | 代码审查、测试、依赖、架构、Git、修复、发布记录 | 未经确认交易、修改账户、把聊天记忆当作计算数据 |
| Atlas Core | 数据获取、计算、风险标记、报告生成 | 代理人格、通道通知、桌面操作 |

### 单一执行契约

后续应形成一个稳定命令，例如：

```text
atlas daily --tickers NVDA MSFT AAPL --output ...
```

OpenClaw 和 Codex 都只调用这一个入口。入口返回机器可读的运行清单：运行时间、代码版本、数据时间、数据来源、成功/降级/失败状态、生成文件列表。通知层只消费这个清单。

### 数据失败原则

```text
真实数据成功 → 生成正式报告
真实数据失败 → 报告标红 + 禁止行动建议
REFERENCE 数据 → 只作历史说明，绝不伪装成当前行情
```

## 六、分阶段建议

### Phase 0：恢复可信运行（先做）

1. 查明 Clash 服务未监听的原因，避免把“socket 文件存在”当作服务健康。
2. 将代理设为显式、可检测、可关闭；删除虚拟环境全局静默注入的依赖。
3. 增加数据源健康检查，并让失败返回非零退出码。
4. 用 AAPL/NVDA/MSFT 做不落盘冒烟测试，确认真实数据时间戳和来源。

### Phase 1：建立工程治理

1. 在用户确认后建立首次 Git 基线；先排除 `.venv`、缓存、敏感配置和生成报告。
2. 新增 `ATLAS_ARCHITECTURE.md`，作为 Codex 与 OpenClaw 共用的系统说明。
3. 新增单一配置文件，统一路径、时区、watchlist、风险规则和数据失败政策。
4. 把现有端到端脚本拆分为无网络单元测试与可控的在线冒烟测试。

### Phase 2：统一执行入口

1. 先编排现有脚本，不重写模型。
2. 为每一步记录开始、结束、数据源、错误和输出。
3. 同日运行使用同一行情快照，避免模块间数据漂移。
4. 保留现有报告路径，并增加统一索引，暂不批量迁移。

### Phase 3：接入日常助手

1. OpenClaw 负责触发和摘要，不直接改投资数据。
2. 通知只发送状态与报告链接；交易、账户和外发重要信息继续要求确认。
3. 手动稳定运行一段时间后，再考虑 launchd；调度不应早于数据健康检查和失败隔离。

## 七、建议下一步

下一次实施建议只做 **Phase 0 + Git 基线设计**，仍不进行大规模重构。验收标准是：

- 代理服务状态可被可靠检测；

- 数据失败时脚本明确失败，不产出貌似正常的正式报告；
- 敏感信息不再硬编码；
- 给出首次 Git 基线的纳入/排除清单，待用户确认后再提交。
